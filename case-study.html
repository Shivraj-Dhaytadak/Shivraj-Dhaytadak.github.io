01 / The Context & Challenge

The 3-Week Bottleneck & LLM Compliance Risk

At Allianz Services, insurance claim lodgement is a high-volume, legally audited domain governed by strict Australia corporate privacy standards. Historically, introducing a new claim journey (such as storm damage, commercial fleet collision, or third-party liability) required 3 weeks of backend engineering: hardcoding domain rules into Python microservices, database schema re-compilations, security audits, and full CI/CD deployment pipelines.

Simultaneously, enterprise leadership recognized that while Large Language Models could automate document triage and intake questions, LLM non-determinism introduced severe operational liability:

  • Adversarial Injection Attacks: Malicious claims payloads attempting prompt injection to bypass settlement policy limits.
  • Citizen PII Leakage: Australian customer identifiers, tax numbers, and medical details risking persistence into unencrypted logging databases.
  • Downstream State Drift: LLMs generating inconsistent JSON schemas that crash backend core insurance systems.
The Architectural Mandate: Build a governed, declarative multi-agent workflow platform that allows claim specialists and prompt engineers to onboard new journeys in < 24 hours without touching underlying codebase binaries, while enforcing 100% deterministic safety guardrails.

Stage 1 (Ingestion): Insurance claim payload received via Azure API Management gateway → queued into Kafka event buffer.

Stage 2 (Multi-Layer Guardrails): Azure Content Safety screens injection attacks → LangChain PII redaction middleware sanitizes citizen data prior to persistence.

Stage 3 (Declarative Graph Engine): JSON execution engine resolves 1 of 19 claim journey state graphs → LangGraph orchestrates cyclic agent nodes.

Stage 4 (Runtime Verification): Every discrete node validates output through strict Pydantic models → eliminates downstream type drift.

Stage 5 (Dual-Emit Observability): Distributed tracing spans emitted concurrently to Azure Application Insights and LangFuse.

03 / Architecture Decision Records (ADRs)

Technical Trade-Offs & Engineering Decisions

ADR-001 ACCEPTED

LangGraph Cyclical State Machine vs. Linear DAGs

Decision: Selected LangGraph over linear DAG pipeline orchestrators (Airflow/Prefect).

Rationale: Real insurance intake requires cyclic evaluation loops: when a claim statement lacks required evidence (e.g., photo of vehicle damage), the agent must dynamically loop back to prompt the claimant, evaluate clarification, and retry without resetting conversation context.

Outcome: Enabled resilient conversational recovery without pipeline failure.
ADR-002 ACCEPTED

Pydantic Runtime Validation at Node Boundaries

Decision: Implemented comprehensive Pydantic v2 schemas validating every input and output at each agent transition.

Rationale: LLM non-determinism frequently produces subtly mutated JSON keys. Without runtime schema enforcement, type errors propagate downstream to enterprise relational databases, corrupting state records.

Outcome: Zero downstream schema drift or database ingestion crashes.
ADR-003 ACCEPTED

Pre-Persistence PII Redaction & Content Safety

Decision: Integrated Azure Content Safety and LangChain PII redaction *before* payload persistence or model transit.

Rationale: Under Australia corporate privacy standards, un-redacted citizen data written to application logs constitutes a regulatory violation. Pre-model filtering halts injection payloads and strips citizen PII upfront.

Outcome: 100% compliance across 100k+ annual insurance claims.
ADR-004 ACCEPTED

Declarative JSON Workflow Engine & Two-Tier Prompts

Decision: Decoupled general insurance guidelines from journey-specific rules using declarative JSON configurations.

Rationale: Rather than compiling Python binaries for every new policy journey, claim paths are defined in JSON contracts. Prompt engineers configure transitions, required documents, and question sequences in JSON.

Outcome: Slashed journey onboarding deployment from 3 weeks to 1 day.
